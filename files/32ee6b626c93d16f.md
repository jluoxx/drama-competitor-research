# 三款短剧应用商业化静态分析

研究日期：2026-11-16。分析对象为本次提取的三个版本，重复包名已去重。使用 competitor-app-analysis 工作流，REA（JADX headless）与 Craft Anything 均已在每款样本完成有效包解析、业务方法和引用查询。本报告提供客户端机制证据，不把包内默认值当作当前线上配置。

## 核心判断

1. **Cash Drama、Coin Short 属于高度相近的奖励短剧实现。** 两者均用 PSSDK 承载短剧，并将签到、新人奖励、观看奖励、双倍奖励、提现受限点击等操作接入广告。过滤资源与绑定类后，`com.kingtar` 类名共有 547 个，类名集合 Jaccard 为 79.6%；这是架构相近的证据，不能据此认定公司归属或相同线上策略。[E001](#e001) [E013](#e013)
2. **不能把 Cash Drama 归为已经验证的 AdMob-only。** 它有 ThinkUp 初始化、TU 激励/插屏状态与比价调用，包内也有 Google Mobile Ads、MAX 等实现。当前供给、聚合后台策略和收入占比仍未知。用户备注“最大一天10w港币”没有收入数据或回调支持，本次不作背书。[E011](#e011) [E003](#e003)
3. **两款奖励短剧的提现成功反馈不等于真实打款。** 追到的 `reqOVSWithdraw` 分支创建金额参数后，调用一个直接构造 `200 / success / true` 的本地方法，再向界面发事件；该方法内没有网络提交。应把“界面显示成功”和“支付到账”分别核实，不能用本链路声称真实可提现，也不能推及所有未覆盖渠道。[E005](#e005) [E017](#e017)
4. **Dramivo 同时包含短剧和桌面 Launcher 能力。** 它声明 HOME Activity、默认桌面引导、桌面通知监听服务；广告栈有 MAX/ThinkUp 路由、切换和比价，而不仅是播放页广告。当前手机未安装该样本，因此默认桌面设置、监听授权及实际广告均未运行验证。[E031](#e031) [E026](#e026) [E032](#e032)
5. **三款都具有远控能力，但没有本次真实线上配置快照。** 前两款按 Firebase AB 分组选择业务 JSON；Dramivo 同时读取策略 JSON 与平铺业务键。自然量/买量的实际差异不能由 SDK 或字段名直接推出。[E007](#e007) [E019](#e019) [E025](#e025)

## Cash Drama：任务与提现预期驱动广告

### 用户路径与广告入口

可支持的流程为：短剧首页/播放 → 观看或任务奖励提示 → 按任务类型选择广告 position → 广告装饰器检查当日数量 → 前N次优先插屏/后续比价 → 广告奖励回调 → 业务奖励展示。现金余额、钱包、提现档位另有实体与界面。广告回调传递响应不证明金币已落库，提现页面成功也不证明真实付款。[E001](#e001) [E002](#e002) [E006](#e006)

| task type | 埋点/场景 | position | 静态含义 |
|---:|---|---:|---|
| 132 | 签到场景 | 6 | 签到奖励广告入口 |
| 134 | new_user_reward | 7 | 新用户奖励入口 |
| 135 | drama_detail_page | 9 | 播放页奖励 |
| 136 | drama_detail_page_double | 10 | 播放页双倍奖励 |
| 301 | withdraw_item_cannot_apply_click | 30 | 提现档位不可申请时的相关入口 |
| 302 | task_unlimited_ad | 31 | 任务页广告入口；名称不取消全局频控 |
| 310 | plana_ad | 35 | Cash版本额外映射；实际触达条件需配合上游按钮/配置验证 |

其他 type 取任务实体的 position，缺实体回退0。以上是映射数量，不等于独立广告单元数，也不等于真实曝光位数。[E001](#e001)

### 广告频控、优先级与失败边界

`KTarIncentiveDecorator.e()` 将 `queryTodayAdShowListCount()` 与 `userDailyMaxAdCount` 比较，达到上限返回拦截。包内JSON为100；无配置对象时也回退100。若对象存在却该int为0，比较本身会使该分支从零计数起被拦截；不能把0解释为无限。该结论限定装饰器覆盖的请求，不推广到所有开屏、原生或SDK内部广告。[E002](#e002)

`i()` 取 `dramaPriorityInterstitialAdCount`：包内JSON为6，无配置对象回退10。计数低于阈值时进入插屏调用，之后进入 `normalLoadAndShow$2`：检查激励和插屏是否准备好，读取 TU ad status/top ad info，比较价格并选择后续分支。两个数值来源必须分开，不能说线上一定是6或10。`interstitialDouble` 被传入后续分支；本报告不根据字段名声称每次必连播两条。[E003](#e003) [E004](#e004)

回前台广告有独立限制：随机1–100与 `switch_rate` 比较、计数与 `switch_num` 比较、时间差与 `switch_sec × 1000` 比较；首次 lastEventTime=0 跳过，栈顶 Activity 包名不含业务命名空间也跳过。包内默认100/4/15对应概率门槛、计数门槛与秒数；真实当日计数重置/成功回调应结合运行数据复核。[E008](#e008)

剧集侧 `isNeedBlock()` 在 `drama_num>0` 时递增 swipeCounter：n>1按整除触发；n=1时首个计数不触发、后续触发广告协程。该方法最终返回false，说明它在回调中调度广告，而非在此返回阻断标记。不能据此说“每集必须看广告才能解锁”。[E009](#e009)

### 奖励与提现的证据边界

`KTarAdFacade$1` 的奖励验证回调设置 `AD_AWARD_RESP`，在后续协程里将响应交给业务 callback。播放页奖励确认分单倍/双倍构造 `OVSReqPositionRewardParams`，传入 `PddRewardParams` 和 amount/lastRewardAmount；日志中的 fake/real 词只是开发实现标记，不能替代余额与付款验证。[E006](#e006)

提现列表由实体提供 `canApply / hasWallet / amount` 等状态。点击不可申请档位会走另一业务入口；可申请但未绑定时给绑定提示。重点链路为：

```text
reqOVSWithdraw$1.invokeSuspend
  → 创建 OVSReqWithdrawParams(amountValue转float)
  → 调用 k04.n()（本方法不接收刚创建的金额参数）
  → 本地 new BaseResponse，code=200，msg=success，data=true
  → checkNullable通过后，向SingleLiveEvent postValue(withdrawInfo)
```

这条成功通路没有服务器订单/转账请求，不能拿界面成功、日志success或回调到达证明打款。需继续用渠道订单号、真实网关响应、余额扣减和外部钱包到账关联核验。本次未提交提现、未填写支付账号。[E005](#e005)

### 远控、人群与召回

`tc2.t` 配置 Firebase、设置本地默认值、调用 fetchAndActivate，并注册配置更新监听。`tc2.z` 从 `abTestGroup` 获取候选分组，缓存组别；按组尝试配置 `_B…_F` 后缀，有键才采用，否则回退无后缀键。解析 `defaultConfigJson_v3` 等JSON到实体并发LiveData，启动页/首页观察者再写入holder；后者将JSON缓存于 `entity`。不同组可以得到不同任务/提现/奖励配置，但当前用户属于哪组、本次线上各键内容均未采样。[E007](#e007)

Adjust network有独立回调与来源状态处理；Firebase AB组来源与归因network来源应分开。`flowGroupingAdvertEnable` 的getter还受平台条件影响，默认无值返回false；它不是“买量用户开启广告”的直接证明。[E012](#e012)

主页启动 UnlockService，动态注册 USER_PRESENT/SCREEN_ON/SCREEN_OFF 并在销毁时注销。解锁分支调用通知构建器，返回非空才notify；亮灭屏分支主要记录日志。FCM接收后检查本地小时8≤h<24、同日间隔超过1小时等条件，再调用通知构建与notify。尚未完整审计构建器内部所有抑制条件，也未触发真机通知。因此只能确认召回能力，不称每次解锁必推送。[E010](#e010)

## Coin Short：相近架构，版本与配置独立

Coin Short 1.0.13.1 与 Cash Drama 分别持有独立 APK、包名、资源与哈希，不能直接复用对方线上值。内容页同样构建 PSSDK DetailFragment 并自动下一集；任务映射中已确认132/134/135/136/301/302，分别对应position6/7/9/10/30/31。本次读取的映射方法没有 Cash 的310分支，其他类型仍依赖任务实体 position。[E013](#e013) [E021](#e021)

广告装饰器方法名不同（cap为c、路由为g），但已交叉读到同样的每日上限、优先插屏和后续比价机制。包内JSON分别给100和6，无配置对象时方法回退100和10。不要用“unlimited_ad”事件名解释成没有上限。回前台也有概率、次数、秒数与当前Activity判断。[E014](#e014) [E015](#e015) [E016](#e016) [E020](#e020)

提现是独立核查过的同类问题：`reqOVSWithdraw$1` 创建金额参数后调用 `wz3.l()`；后者同样在本地构造200/success/true，并由ViewModel向界面发事件。本结论来自 Coin 自己的字节码，不是从 Cash 推测。它不提供真实转账证据。奖励回调同样把响应传给业务 callback，后续实际余额、日限额、跨天恢复和渠道打款仍需实测。[E017](#e017) [E018](#e018)

远控holder是tk2，配置仓库是hb2。`hb2.z/t` 按AB组解析配置、激活Firebase并更新业务数据，支持任务、提现、奖励等级、签到和召回配置等；包内默认JSON里有多币种新人奖励，不能据此推断当前地区实际送钱金额。业务常量域名为 `coindrama.balaleek.com`；Cash为 `coindramaapi.balaleek.com`，只是客户端声明的地址，并未验证服务现状或公司关系。[E019](#e019) [E023](#e023)

FCM和解锁通知入口分别在 Coin 样本中读取过，具备相近的时段/间隔与通知落点机制。Adjust回调也单独定位，当前没有真实归因结果，不能从同架构推导当前投放渠道或人群收入差异。[E022](#e022) [E024](#e024)

## Dramivo：短剧、桌面承接和多路广告

### 产品结构与桌面引导

包内标签为“🔥Dramivo”，包名仍为dramapop，业务类使用 `com.freetools.freereels`。Manifest中的 `com.android.launcher3.Launcher` 已启用并导出，具有MAIN/HOME/DEFAULT intent-filter；这属于本APK的桌面实现，不是扫描到系统应用。`Q.p(Activity)` 检查默认HOME并创建引导框，`thirdsdk.e.c` 先受X状态约束，限频分支使用300000ms。默认 `SplashPopLauncher=false / MainPopLauncher=true / DetailPopLauncher=false`；配置可以覆盖，不能据此说当前每个入口都会要求设桌面。[E031](#e031) [E028](#e028)

引导点击的实际消费者为 `zc.g.g(Activity)`：先检查当前默认HOME；已设为本应用则提示。Android 10及以上、特定本地计数字段为0时，在HOME角色可用且尚未持有的条件下调用 `RoleManager.createRequestRoleIntent("android.app.role.HOME")` 并启动请求；另一分支打开 `android.settings.HOME_SETTINGS`。这是请求系统默认桌面设置的链路，仍需用户在系统界面选择。[E031](#e031)

桌面图标启动追到 `Launcher.w → BaseDraggingActivity.w`，按用户/快捷方式分支调用 `startActivity` 或 `LauncherApps.startMainActivity` 并记录启动；已读 `Launcher.onResume/A` 及其500ms协程中未定位直接广告展示。因此本次不支持“每次回桌面或点击图标必出广告”的结论，其他入口仍需真机覆盖。[E033](#e033)

通知服务 `onNotificationPosted` 将通知包装后发送到Handler；构造器把后台Handler绑定到Launcher模型线程，`I8.e.handleMessage case3` 将新增/移除消息转发到主线程，刷新消息尝试获取活动通知并捕获SecurityException。过滤方法 `NotificationListener.b` 读取标题/正文，结合角标排名、持续通知和分组摘要条件筛选；`c` 处理通知key/groupKey等。这些支持桌面通知处理能力，不能证明已获通知使用权或已上传内容。[E032](#e032)

`DetailActivity.finish()` 在 `X()` 通过时尝试展示其他短剧推荐；过滤当前剧，从候选里取最多5条并重复填充轮播，缺数据则直接finish。这个动作首先是退出留存机制，不能自动称为退出广告。[E034](#e034)

### 广告选择与播放页频控

FreereelsApp 读取包内MAX和ThinkUp初始化参数，`c.b.a()` 在配置允许并且两路准备好时进入价格比较：从MAX对象取得revenue乘1000，再将信息交给ThinkUp自定义内容评审接口。`mediationPriceCompareV1` 控制该分支；仅字段存在不能证明线上开启。`mediationSwitchImmed>0` 或无策略对象时，准备状态允许检查两路，首选展示失败会尝试另一条；否则仅走选定路线。[E026](#e026)

播放页 `l6.j.onItemSelected` 要求index>0、间隔>0、index%interval=0、index不同于Intent中的初始extra_index，满足后调度l6.g协程。协程先等待1000ms，再检查当前时间与静态广告时间戳之差是否达到2000ms；不足则跳过，达到后更新时间戳并调用 `ad.c.a("detail-inner")`。间隔getter来自 `DetailAdInterval`，包内默认3，是按index的次数条件，不能解释为3秒；2秒时间戳门槛是另一层条件。原生位置提供器使用 `DetailNativeAdInterval+1` 为步长，从0生成候选位置，范围至少100；默认1000意味着步长1001，不等于当前实际已有1000次或每1000秒出广告。[E029](#e029) [E028](#e028)

当前已追到的普通广告显示接口、准备状态和配置回退足以证明多路能力；真实无填充、关闭后恢复、实际展示次数、收入回调仍缺运行观察。包内有购买相关通用SDK字符串也不能证明业务订阅，本轮未还原有效SKU/付费墙/购买确认链。

### 在线来源与分层决策

`zg.c.e` 发起配置任务并接续激活/读取回调，外层30,000ms节流是配置操作节流，不是广告冷却。成功回调读取 `ad_strategy_json_config`，经 `j.c.a` 解析，再通过 `yg.a.run case0` 更新 `yg.b` 策略对象和本地缓存。`server_attributed` 为真时将来源状态置bit8。另一路 `Ec.a.run case5` 将平铺业务键写入data枚举缓存。[E025](#e025) [E028](#e028)

| 输入/状态 | 已确认动作 | 对业务的可支持解释 |
|---|---|---|
| AdjustAttribution为空或network空 | 回调不更新 | 当前未知状态不能当作Organic |
| network转小写后包含untrusted | is_suspect设为真并缓存 | 可影响后续X判断，不推断检测用途 |
| network包含organic | 本回调不置bit16 | 不代表其他来源bit为0 |
| 非上述network | 来源状态OR bit16，写user_source | 非自然来源是可置位来源之一 |
| Firebase server_attributed=true | OR bit8 | 服务端标记也是来源之一 |
| X() | user_source>0 且 !is_suspect | 已明确用于推荐/桌面引导等消费者；不能推广为全部广告的唯一开关 |

### 推送与活跃条件

默认通知JSON包含open=true、startHour=7、endHour=21、intervalSec=43200、createAfterClear=true、createAfterClearSec=60、noticationIdCnt=1、lastActiveSec=86400、showInForeground=false。正常调度判断间隔时使用 `intervalSec×1000` 且小时范围为[7,21)；缺失intervalSec的单独fallback为14400，两种来源不要混写。[E030](#e030)

`notification.d.a` 比较 `currentTimeMillis()-LastActiveTime <= lastActiveSec` 时，所读方法内没有将后者乘1000。因此默认86400参与该比较的是毫秒差值，约86.4秒；不能把这个实现直接写成“24小时不活跃才推送”。这是静态单位不一致线索，仍需确认线上取值与LastActiveTime赋值时序。[E030](#e030)

通知正文使用短剧封面、标题/描述与播放CTA；PendingIntent进入SplashActivity，携带 `extra_from_notification=true` 与 `short_play_data`。deleteIntent指向LocalNotificationReceiver，清除后分支读取createAfterClear与60秒节流，再调用生成逻辑；它不是保证清除60秒后一定重发的定时器。内容加载失败、封面为空、通知权限、系统Job限制都可能影响最终可见结果。[E030](#e030)
