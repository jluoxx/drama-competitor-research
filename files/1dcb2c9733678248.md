# 三款短剧应用 AdMob 关键词专项

研究日期：2026-11-16。范围仅为前面已提取的三款短剧 APK，截图中的工具应用不在本次范围。沿用 competitor-app-analysis 技能，实际使用 REA 与 Craft Anything，核查请求、输入来源、去重、上报、缓存与更新链。分析在电脑上针对已有APK完成，未启动三款目标应用进行广告请求、点击广告或抓取手机账号数据。

## 先回答你的四个问题

| 问题 | 本次结论 | 不能扩大为的结论 |
|---|---|---|
| 关键词是否分页？ | 三款已读普通AdMob适配链均遍历整个输入List，未找到page/offset/cursor、subList、每批N词、轮询索引或耗尽换页逻辑。 | 不能证明Google内部服务端不分页；不能排除未提供的动态代码。 |
| 是否上报？ | 都有ThinkUp事件1004701，携带关键词列表字符串、内容URL等；走异步队列、过滤和本地存储/发送任务。 | 事件构造不等于发送成功，更不等于服务端收到；不是Firebase埋点的直接证据。 |
| 关键词有无上限？ | 适配器不截断；addKeyword底层将String加入HashSet，已读链路无条数或单词长度阈值。 | 不能说“平台无限制”。512是内容URL长度限制，不是512个关键词。 |
| 首次和二次会换词吗？ | 同一输入、同一路径、每次新请求会得到相同去重集合；未发现按请求次数自动换词。 | 不能把它写成已抓到两次相同网络请求；本次没有请求载荷实测。 |

**最重要的边界：三款都具备传关键词的SDK能力，但本次没有找到业务层显式设置关键词词库的调用，也未取得实际关键词值。不能把“支持关键词”写成“当前广告必带关键词”，更不能凭空列出保险、金融、贷款等词。**

## 1. 关键词从哪里来：本地extra，不是自动生成的词库

普通路径还原为：

```text
setLocalExtra(Map)这一SDK公开能力
  → common.d0.m(Map)
  → no.dn.d(Map)：复制非空key/value，保留List值对象
  → dq0.d(Map)：替换本地Map引用
  → 每次load准备时 common.d0.n0()：new HashMap + putAll
  → common.dd.dm → nq.o.d0 → nq.q.do()
  → 作为extra Map传给AdMob适配器
  → extra["admob_keywords"] → addKeyword
```

其中no.dn.d(Map)仅对key_width/key_height等尺寸字段做数值转换；没有对关键词List做分页、截断或随机抽取。dq0.m()是直接返回保存的Map，dq0.d(Map)是替换引用，初始构造器没有给关键词Map填默认词库。n0()在同步块内复制Map；这是浅拷贝，不会深拷贝其中List。后续外部若原地修改List，下一次读取可能看到新内容；这属于输入变化，不能称作分页。

setLocalExtra只表示SDK接口存在。本次对三款base业务/聚合SDK指令做定向扫描，admob_keywords字面量各只落在SDK读取、适配注入与常量定义位置，未找到业务层词库赋值；也未找到业务调用setLocalExtra。Cash/Coin有initCustomMap调用，但传的是channel字段，不能把它当关键词列表。扫描范围、命中位置与调用片段见[scan-summary.json](scan-summary.json)。

三款上轮查到的Firebase业务远控、AB分组和归因状态，不能直接拼接为关键词来源：本次没有找到“某个Firebase关键词JSON → 本地extra.admob_keywords”的业务赋值链。也没有取得实际服务端词库、抓包词值或账号级关键词配置。原生库、反射、动态模块与服务端可能带来进一步条件，这些未覆盖项不能反过来当作已存在的词库。

## 2. 请求如何取词：整体遍历、类型过滤与去重

适配方法先处理内容URL，再读取第二个Map（本地extra）的admob_keywords。只有该值是List且非空才遍历：

```java
Object value = extras.get("admob_keywords");
if (value instanceof List && !((List)value).isEmpty()) {
    for (Object item : (List)value) {
        if (item instanceof String) builder.addKeyword((String)item);
    }
}
```

它不是“从大词库取前10个”，没有页码、偏移、步长、请求次数、随机种子、shuffle、remove首元素或已使用词集合。builder构造路径每次new AdRequest.Builder，再调用上述注入方法；此处不复用上一次builder逐次累积关键词。

Google SDK链为AbstractAdRequestBuilder.addKeyword → 内部zzeg.zza(String) → HashSet.add(String)。因此重复的完全相同字符串会去重，输入顺序也不能当作优先级或最终序列保证。所读链路没有转小写、trim、按逗号分词、翻译或语义归并："loan"、"Loan"、" loan "属于不同字符串。若List中一个元素是"loan,insurance"，适配器将其作为一个String传入，不会在这里拆成两个词。

| 输入情况 | 已读客户端行为 | 上报与最终集合的区别 |
|---|---|---|
| 缺键/null/不是List | 不进入关键词循环 | 关键词字符串未构造；URL为List时仍可能触发事件 |
| 空List | 不调用addKeyword | List.toString得到"[]"，其字符串非空，上报条件仍可能成立 |
| ["drama","drama"] | 两次调用addKeyword，HashSet最终一个相同值 | 埋点仍保留两个条目的列表表示 |
| ["Drama","drama"] | 未做大小写归并 | 后端如何解释未知 |
| ["", "  "] | 通过String类型检查；所读addKeyword实现直接入Set | 不证明Google后端接受或用于匹配 |
| ["drama",123,null] | 仅String进入关键词集合 | List.toString仍可包含123、null |
| 单个逗号分隔字符串 | 一个元素；没有在适配器分词 | 不能由逗号数量推算关键词数量 |

此表是代码条件推演，不是对真实广告SDK执行上述输入后的网络测试。

## 3. 数量上限：分清词库、单次请求和平台边界

在已读“输入Map清洗 → 本地保存 → 加载快照 → 适配器循环 → Google HashSet”中，没有找到关键词总数、单次词数、词长度、按天用词次数或首次/二次取词上限。不存在本次可以支持的“每次最多N个关键词”具体值。

这只能说明**这条客户端链没有显式上限检查**。服务端可能忽略字段、限制载荷、采用自己的匹配或容量规则，底层通信也有资源边界；本次没有Google服务端响应或官方文档快照来确认平台的完整限制。因此不能把结论写成“AdMob允许无限关键词”，也不能把无填充直接归因于关键词超限。

与关键词相邻的512限制属于setContentUrl(String)：不允许null、空串、长度超过512的URL。它不是关键词条数，也不是关键词单词长度。setNeighboringContentUrls经过另一方法清空内部URL列表再过滤空URL，所读方法没有与关键词共用配额。

## 4. 首次与二次：哪些情况会相同，哪些可能改变

| 情况 | 关键词集合判断 | 原因与边界 |
|---|---|---|
| 同一广告管理对象、同一extra、两次普通AdMob新load | 按代码应相同的去重集合 | 每次新builder，遍历同一输入；没有自动翻页 |
| 首次无填充后再次load，输入没变 | 所读链路不因失败自动换词 | 不把业务重试等同于词库重试 |
| 第二次只是展示缓存广告 | 可能根本没有第二次广告请求 | 当前展示不能代表当前词表已重新提交 |
| 上层重新setLocalExtra，替换词表 | 下一次取快照可能改变 | 保存方法替换Map，不是在此合并旧词库 |
| 同一List被上层原地改写 | 下一次可能变化 | Map快照浅拷贝；不保证并发修改安全 |
| 换广告位/管理对象，或重建实例 | 可能不同，也可能默认空 | 本地模型按对象持有；没有在此发现持久化的关键词分页游标 |
| 词表仅改顺序、完全相同词重复次数变化 | 去重集合可保持相同 | 埋点列表字符串可能变化；不能据此说最终定向集合变了 |
| URL设置抛异常 | 本次关键词循环可能没执行 | URL处理和关键词循环在同一个try/catch内 |
| 切到已读AdManager构造分支 | 该构造方法未复用上述关键词注入 | 需确认实际路由；不以SDK存在推断当前走向 |

所以，“二次关键词有没有变”应比较两次**实际新建广告请求**的词集合、extra快照与路由；比较两次曝光、两条埋点或不同格式的广告位，都不足以单独回答。

## 5. 上报链：事件1004701实际记录什么

取extra的nq.q.do()在network标识等于2时检查：URL对象是否为List，或关键词List的toString结果是否非空。满足其一则调用nn.d0.d(...)创建事件1004701。注意这个条件不是“最终Google请求里至少有一个有效关键词”。

| 内容 | 构造/序列化对应 | 含义 |
|---|---|---|
| 事件号 | 1004701 | ThinkUp SDK事件构造方法明确赋值 |
| unitid | 取词链传入的广告位标识 | 能用于关联位置，不能自动当作Google广告单元ID |
| groupid/unitgroupid及其他配置字段 | 从m0对象填入 | 聚合/广告源上下文字段；不据名称猜业务归因 |
| msg4 | 固定传admob_content_urls | 即使触发原因是关键词，这个字段也不是admob_keywords |
| msg5 | URL对象.toString，null回退空串 | 可能是列表表示；不是结构化JSON数组承诺 |
| msg6 | 关键词List.toString | 例如[drama, romance]；不是逐词JSON编码 |
| timestamp等 | 后续补时间/上下文 | 不等于曝光时间或Google收到请求的时间 |

上报列表在去重、String过滤和真正Google请求成功之前获取，因此可能有重复词、非String元素或"[]"。输入中词本身带逗号、方括号时，List.toString不能可靠无歧义反解析。msg6存在并不证明相同词已用于一次成功广告请求，更不证明影响了填充或价格。

已追到的链路为：事件对象 → 初始化/上下文检查 → 异步任务队列 → 全局关闭与事件规则过滤 → nd.d()序列化 → 本地事件记录 → flush任务。过滤会参考事件号对应配置，部分条件可直接丢弃；本次没有实际事件配置值。事件队列的批量处理属于**统计事件批次**，不能当作**关键词分页请求**。

flush进一步从本地记录提取事件字符串列表，按SDK配置od选择常规md.q或另一md.o.m请求对象，执行SDK网络发送接口。另一模式将每条事件还原为JSONObject，装入data JSONArray，补app_id、nw_ver等上下文，转换并封装为p等外层字段后交给字节数组构建方法。这里确认的是事件会进入网络请求构建路径，不声称其传输内容一定是可直接搜索的明文。

常规md.q的目的地址来自common.dn.q()：依据SDK状态选择默认地址，再经agent域名处理；远端配置do0存在时可参与覆盖。另一模式从配置o0取得路由参数。因此包内默认域名、当前实际目标、请求发出和服务器收到是四个不同证据层；本次没有主动请求这些统计接口。文件名172_alt_report_url对应的方法实际返回封装后的JSON字符串，不能因文件名把它当成真实URL。

三款常量源均定义dq=`https://da.robin-flow.com/v1/open/da`，dn$q初始化复制到dq，并通过https替换为http生成qn，地址getter在这两者间选择后再做覆盖处理。这是本链的包内默认候选；`https://tk.robin-flow.com/v1/open/tk`等另有常量，不能只因同属统计域名就把它认作本事件的已执行目标。未验证域名归属，也未访问这些统计接口。

没有发现本链在关键词读取器里上传搜索历史或自动把短剧搜索词写进admob_keywords的业务调用。搜索接口里也出现keyword一词，但不能据相同字符串就把“用户搜索短剧”与“广告关键词”认作同一数据流。SDK具备发送能力与服务器接收事实仍分开记录。

## 6. 其他会影响判断的细节

### 内容URL与关键词是两个通道

内容URL优先取extra.admob_content_urls；缺失/空时回退第一个Map中的web_content_urls（JSONArray）。一个URL走setContentUrl，多个走setNeighboringContentUrls。关键词只从第二个extra Map的admob_keywords读取，所读适配器没有为关键词写出相同的远端Map回退逻辑。

URL先于关键词处理且共用try/catch：单URL为空或超512可能抛异常，使本次addKeyword尚未执行就退出；而关键词事件可能已在更早取extra时构造。由此可能出现“有关键词埋点，但本次builder没加入关键词”。多个URL的空值过滤则属于另一路径，不应与单URL校验混为一谈。

### 广告格式与请求家族

AdMobTUInitManager被Banner、Interstitial、Rewarded、Splash、Native等适配类引用，普通builder注入方法具有共用性质；这说明多个格式可复用能力，不证明每个格式当前都有词。另一个AdManagerAdRequest.Builder构造重载中只看到网络extras配置，没有普通builder的关键词注入调用；当前应用实际走哪一支需以实际加载路径判断。

network extras中还处理gdpr_consent对应npa、rdp、query_info_type、可折叠Banner、hybrid状态和placement_req_id等。这些与关键词通道不同，不能把它们解释成关键词分页标志；mediation_request_id也不等于词库页码。

### 不能由关键词代码推出的效果

不能推断某词“高价”、某应用靠关键词提高eCPM、收入达到特定金额、平台认可其定向方式，也不能由此判断审核规避或政策违规。Cash Drama的AdMob-only备注仍未得到实际供给证据；本次关键词专项不会把SDK能力当平台占比。
